# コード品質ルール

## コーディングスタイル

### TypeScript規約
- 型定義を明示的に行う
- `any`型は極力使用しない
- インターフェースや型エイリアスを積極的に使用する
- Nullableな値は`undefined | T`のように明示的に型定義する
- 関数の引数と戻り値の型は必ず定義する

### 変数・関数命名規則
- 変数名：キャメルケース（camelCase）
- 関数名：キャメルケース（camelCase）
- コンポーネント名：パスカルケース（PascalCase）
- 定数：大文字スネークケース（UPPER_SNAKE_CASE）
- 型名：パスカルケース（PascalCase）
- boolean変数：`is`、`has`、`should`などのプレフィックスを使用

### インポート規則
- 絶対パスを使用する
- インポートの順序：
  1. 外部ライブラリ
  2. 内部モジュール
  3. 型定義
  4. スタイル

### コメント規則
- 複雑なロジックには必ずコメントを付ける
- TODOコメントには担当者と期限を記載する
- 一時的な回避策にはその理由を記載する
- JSDocスタイルのコメントを推奨

## コード構造

### 関数設計
- 関数は単一責任の原則に従う
- 副作用を最小限に抑える
- 関数の長さは20〜30行以内に収める
- 早期リターンパターンを使用する

### エラーハンドリング
- try-catchブロックを適切に使用する
- エラーオブジェクトは具体的な情報を含める
- ユーザー向けエラーメッセージは親切で明確にする
- 開発者向けデバッグ情報はログに記録する

### 非同期処理
- Promise.all()を使って並列処理を最適化する
- async/awaitを基本とし、thenチェーンは避ける
- エラーハンドリングを適切に実装する
- 非同期処理の状態（loading, error, data）を管理する

## テスト

### テスト戦略
- 重要なビジネスロジックには単体テストを書く
- UIコンポーネントには結合テストを書く
- E2Eテストで重要なユーザーフローをカバーする

### テストの命名規則
- テストファイル名は`[テスト対象].test.ts(x)`とする
- テストケース名は「何をテストするか」が明確にわかるようにする

## パフォーマンス最適化

### レンダリング最適化
- 不要な再レンダリングを避ける
- メモ化（useMemo, useCallback）を適切に使用する
- 大きなリストはページネーションや仮想化を検討する

### データフェッチング最適化
- 必要なデータのみ取得する
- キャッシュを活用する
- 適切なタイミングでデータを取得する（遅延ロードなど）

### バンドルサイズ最適化
- 不要なライブラリの削除
- コードスプリッティングの活用
- 画像最適化

## アクセシビリティ

### 基本ルール
- 適切なHTML要素を使用する（セマンティックHTML）
- キーボード操作に対応する
- スクリーンリーダーに配慮する
- コントラスト比を確保する

### ARIA属性
- ARIA属性を適切に使用する
- ロール（role）を明示的に定義する
- 状態（state）を適切に管理する

## セキュリティ

### 入力検証
- ユーザー入力は必ずバリデーションを行う
- バックエンドでも再度バリデーションを行う
- SQLインジェクションやXSSを防止する

### 認証・認可
- 認証情報の適切な管理
- 権限チェックの徹底
- セッション管理の適切な実装

## リンター・フォーマッター

### Biome設定
- Biomeの推奨設定を使用する
- エラーは修正し、警告は検討する
- コミット前にlintを実行する
